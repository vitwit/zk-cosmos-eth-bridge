# Deployment Guide

This guide provides step-by-step instructions for deploying the ZK-bridge contracts to a production-like environment (Cosmos EVM Source and Ethereum Destination).

## 1. Prerequisites

- **Private Key**: An account with native gas tokens on both chains
- **RPC URLs**: 
  - Source: A Cosmos EVM RPC (e.g., Evmos, Cronos, or your local Ethermint node)
  - Destination: An Ethereum RPC (e.g., Sepolia, Mainnet, Hardhat, or Anvil)
- **Tooling**: Go 1.21+, Node.js & npm (for Hardhat deployment)
- **ZK Circuit Compiled**: Run compiler first to generate `Verifier.sol`

## 2. Compile ZK Circuit

**IMPORTANT**: Run this first to generate the Verifier contract and keys.

```bash
cd zk-bridge
go run cmd/compiler/main.go
```

This generates:
- `keys/proving.key` - Used by relayer for proof generation (~450MB)
- `keys/verifying.key` - Verification key
- `contracts/Verifier.sol` - Solidity verifier contract with patched SHA256 logic

## 3. Deploying to Cosmos EVM (Source)

The `BridgeSource.sol` contract is responsible for locking assets and emitting the `Locked` event.

### Option A: Deployment via Remix IDE

Remix is a powerful browser-based IDE for quick deployments.

1. Open [Remix IDE](https://remix.ethereum.org)
2. Upload `contracts/BridgeSource.sol`
3. Go to **Solidity Compiler** tab and click **Compile**
4. Go to **Deploy & Run Transactions** tab
5. Set **Environment** to:
   - **Injected Provider** (if using MetaMask connected to Cosmos EVM)
   - **Custom RPC** (paste your Cosmos EVM RPC URL)
6. Click **Deploy** (no constructor arguments needed)
7. **Record the address**: `0xBRIDGE_SOURCE`

### Option B: Deployment Script (`deploy_source.js`)

```javascript
import { ethers } from 'ethers';
import fs from 'fs';

async function main() {
    const provider = new ethers.JsonRpcProvider('YOUR_COSMOS_EVM_RPC');
    const wallet = new ethers.Wallet('YOUR_PRIVATE_KEY', provider);

    const abi = JSON.parse(fs.readFileSync('./artifacts/contracts_BridgeSource_sol_BridgeSource.abi', 'utf8'));
    const bin = fs.readFileSync('./artifacts/contracts_BridgeSource_sol_BridgeSource.bin', 'utf8');

    const Factory = new ethers.ContractFactory(abi, bin, wallet);
    const contract = await Factory.deploy();
    await contract.waitForDeployment();

    console.log("BridgeSource deployed to:", await contract.getAddress());
}
main();
```

### Option C: Using Cast (Foundry)

```bash
cast send --create $(cat BridgeSource.bin) \
  --rpc-url $COSMOS_EVM_RPC \
  --private-key $YOUR_PRIVATE_KEY
```

## 4. Deploying to Ethereum (Destination)

Deployment on the destination involves two steps: deploying the ZK Verifier and then the Bridge contract.

### Step A: Deploy Verifier

The `Verifier.sol` is generated by the ZK circuit compiler and contains the Groth16 verification key.

**Using Remix:**
1. Upload `contracts/Verifier.sol` (generated by compiler)
2. Compile it
3. Deploy (no constructor arguments)
4. **Record the address**: `0xVERIFIER`

### Step B: Deploy BridgeDestination

The `BridgeDestination` requires:
- `_verifier`: Address of deployed Verifier
- `_initialRoot`: The transaction Merkle root of a valid Cosmos block

**Getting the Initial Root:**

In Tendermint, the transaction Merkle root is stored in the block header as `data_hash`.

```bash
# Fetch current root from Cosmos
curl -s http://localhost:26657/block | jq -r '.result.block.header.data_hash'
```

**Example output:** `E3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855`

**IMPORTANT for Remix**: Prefix with `0x`:
```
0xE3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855
```

**Using Remix:**
1. Upload `contracts/BridgeDestination.sol`
2. Compile it
3. Deploy with constructor arguments:
   - `_verifier`: `0xVERIFIER` (from Step A)
   - `_initialRoot`: `0xE3B0...` (from curl command above)
4. **Record the address**: `0xBRIDGE_DEST`

### Deployment Script (`deploy_destination.js`)

```javascript
import { ethers } from 'ethers';
import fs from 'fs';

async function main() {
    const provider = new ethers.JsonRpcProvider('YOUR_ETHEREUM_RPC');
    const wallet = new ethers.Wallet('YOUR_PRIVATE_KEY', provider);

    // 1. Deploy Verifier
    const vAbi = JSON.parse(fs.readFileSync('./artifacts/contracts_Verifier_sol_Verifier.abi', 'utf8'));
    const vBin = fs.readFileSync('./artifacts/contracts_Verifier_sol_Verifier.bin', 'utf8');
    const VFactory = new ethers.ContractFactory(vAbi, vBin, wallet);
    const verifier = await VFactory.deploy();
    await verifier.waitForDeployment();
    const verifierAddress = await verifier.getAddress();
    console.log("Verifier deployed to:", verifierAddress);

    // 2. Get initial root
    const initialRoot = "0xE3B0C44298FC1C149AFBF4C8996FB92427AE41E4649B934CA495991B7852B855";

    // 3. Deploy BridgeDestination
    const bAbi = JSON.parse(fs.readFileSync('./artifacts/contracts_BridgeDestination_sol_BridgeDestination.abi', 'utf8'));
    const bBin = fs.readFileSync('./artifacts/contracts_BridgeDestination_sol_BridgeDestination.bin', 'utf8');
    const BFactory = new ethers.ContractFactory(bAbi, bBin, wallet);
    const bridge = await BFactory.deploy(verifierAddress, initialRoot);
    await bridge.waitForDeployment();

    console.log("BridgeDestination deployed to:", await bridge.getAddress());
}
main();
```

## 5. Root Management

### Understanding Trusted Roots

The `BridgeDestination` contract maintains a `trustedRoot` - the Merkle root of Cosmos transactions it will accept proofs for.

### Updating the Root

**Option 1: Via Relayer (Automated)**
The relayer automatically calls `updateTrustedRoot` before submitting proofs.

**Option 2: Manual Update (Remix)**
1. Load your deployed `BridgeDestination` contract in Remix
2. Call `updateTrustedRoot(bytes32 _newRoot)`
3. Get the new root:
   ```bash
   curl -s http://localhost:26657/block | jq -r '.result.block.header.data_hash'
   ```
4. Prefix with `0x` and submit

## 6. Configure Relayer

Update your `.env` file in the project root:

```bash
# Copy template
cp .env.example .env

# Edit with your values
nano .env
```

**Required values:**
```bash
COSMOS_WS_URL=ws://localhost:26657/websocket
COSMOS_RPC_URL=http://localhost:26657
COSMOS_EVM_RPC_URL=http://localhost:8545
ETHEREUM_RPC_URL=http://localhost:8545
BRIDGE_SOURCE_ADDR=0xYOUR_SOURCE_ADDRESS
BRIDGE_DEST_ADDR=0xYOUR_DEST_ADDRESS
RELAYER_PRIV_KEY=your_private_key_here
```

## 7. Interaction Workflow

Once deployed:

1. **Lock on Source**: Call `lock(recipient)` on the `BridgeSource` contract, sending the `amount` as `msg.value`
2. **Generate Proof**: The relayer detects the event, fetches the Merkle path from Cosmos RPC, and generates a SNARK proof
3. **Mint on Destination**: Relayer calls `mint(...)` on `BridgeDestination` with the proof to mint tokens on Ethereum

## 8. Locking Tokens (Testing)

### Via Remix
1. Load `BridgeSource` contract in Remix
2. Connect to Cosmos EVM network
3. In the **Value** field (above the contract functions), enter amount in Wei (e.g., `1000000000000000000` for 1 ETH)
   - **Note**: This field is global, not inside the `lock` function box
4. In the `lock` function, set `recipient` to your Ethereum address (e.g., `0xC6Fe5D33615a1C52c08018c47E8Bc53646A0E101`)
5. Click **lock** button
6. Confirm transaction

### Via CLI (Cast)
```bash
cast send 0xBRIDGE_SOURCE "lock(address)" 0xRECIPIENT_ADDRESS \
  --value 1ether \
  --rpc-url $COSMOS_EVM_RPC \
  --private-key $YOUR_KEY
```

### Via Cosmos SDK CLI (Ethermint/Evmos)
```bash
evmosd tx evm send 0xBRIDGE_SOURCE "lock(address)" 0xRECIPIENT_ADDRESS \
  --value 1000000000000000000 \
  --from mykey \
  --chain-id evmos_9000-1
```

> [!IMPORTANT]
> The `recipient` must be a standard Ethereum `address`. Do NOT pad it with zeros.

## 9. Network-Specific Notes

- **Cosmos EVM (Ethermint)**: Ensure your gas limit is set high enough, as Cosmos EVM chains sometimes have different gas estimation behaviors compared to standard Geth
- **Layer 2s**: If deploying to Arbitrum or Optimism, the `Verifier.sol` might require minor opcode adjustments if the L2 doesn't support the full range of Ethereum precompiles (though BN254 pairing is standard on most)
- **Testnets**: For Sepolia or other testnets, ensure you have sufficient testnet ETH for gas

## 10. Interacting with Deployed Contracts (Remix)

### How to Load an Existing Contract

If you refresh Remix or want to interact with a contract you deployed earlier:

1. Ensure you have the exact same source code open and **Compiled**
2. Go to the **Deploy & Run Transactions** tab
3. Ensure the correct contract is selected in the **Contract** dropdown
4. In the **At Address** field (right above the deployed contracts list), paste the address of your previously deployed contract
5. Click the **At Address** button
6. The contract instance will appear in the **Deployed Contracts** list, allowing you to call its functions

### How to "Update" a Contract

Smart contracts are immutable. To change the logic, you must **redeploy**:

1. Apply your changes to the `.sol` file
2. Go to the **Solidity Compiler** tab and click **Compile**
3. Go to the **Deploy & Run Transactions** tab
4. Click **Deploy** again
5. **Note**: This creates a **new address**. You must update your `.env` file with the new addresses

## 11. Troubleshooting

### Contract Deployment Fails
- Check you have sufficient gas on the deployment chain
- Verify RPC URL is correct and accessible
- Ensure constructor arguments are properly formatted (prefix bytes32 with `0x`)

### Verifier.sol Not Found
- Run `go run cmd/compiler/main.go` first
- Check that `contracts/Verifier.sol` was generated

### Root Mismatch Errors
- Ensure the root in `BridgeDestination` matches a valid Cosmos block
- Use `curl` command to get current root
- Remember to prefix with `0x` in Remix

## 12. Data Migration & Upgradability

In a production environment, you may need to migrate state between contract versions.

### Strategies:
1. **Manual Migration**: Emit `Migrated` events and have the relayer reconstruct the state on the new contract
2. **Proxy Patterns**: Use OpenZeppelin UUPS or Transparent Proxies to keep the bridge address constant while upgrading logic
3. **State Reconstruction**: Since all bridge actions are recorded on-chain, a new contract can "replay" the history from genesis if needed
